# lovetech v67 — безопасная подготовка Timeweb Cloud

## Что исправлено
Dockerfile теперь копирует **все** необходимые модули и HTML-шаблоны из репозитория. `.dockerignore` исключает базы данных, резервные копии и секреты. Код бизнес-операций v67 не менялся.

## 1. Сначала определите состояние существующего приложения
Откройте Timeweb Cloud → Приложения (App Platform) → существующая lovetech.
Запишите: состояние приложения, источник GitHub/ветку, тип сборки (Dockerfile), статус последнего деплоя, URL, переменные окружения (только **названия**, не значения), наличие подключённого постоянного тома и его путь.
Откройте URL приложения и URL `/health`, `/health/ready` (не делайте вывод о сохранности базы только по ответу `/health`).
**Не удаляйте приложение и тома; не запускайте новое развёртывание до проверки данных.**

## 2. Проверка сохранности SQLite
Проверьте, что `CHEM_DB=/app/data/chem.db`, а `/app/data` действительно сохраняется между деплоями (постоянный том или другое подтверждённое постоянное хранилище). Не полагайтесь на файловую систему контейнера. Если постоянного хранилища нет или оно неизвестно, остановите обновление до получения копии существующей БД.
Для копии из доступного контейнера: `python db_maintenance.py backup --db /app/data/chem.db --output /app/data/backups/predeploy-YYYYMMDD.db` (подставьте дату, заранее проверьте каталог и права). Выгрузите копию **вне** приложения и проверьте возможность её прочитать. Не храните единственную копию на том же томе.

## 3. Подготовка GitHub
Создайте отдельную ветку `deploy-v67`, поместите **содержимое** архива в корень репозитория (включая Dockerfile и HTML-шаблоны). Не загружайте `.env`, `chem.db` или резервные копии. Сначала разверните тестовый экземпляр на копии базы, не подключая production-том одновременно к двум приложениям.

## 4. Конфигурация Timeweb
Сборка: Dockerfile из корня репозитория. Контейнер слушает `0.0.0.0:8080`. Настройте порт приложения 8080 в панели.
Переменные окружения: `SECRET_KEY` (не менее 32 символов), `ADMIN_PASSWORD` (не менее 12 символов), `CHEM_DB=/app/data/chem.db`. Секреты вводятся в панели Timeweb, не в GitHub. Для тестового экземпляра используйте отдельные секреты и отдельную копию SQLite.
Внимание: `entrypoint.py` при старте выполняет `init()` и может обновлять структуру базы; никогда не направляйте непроверенный тестовый деплой на production SQLite.

## 5. Проверка перед переключением
После старта проверьте `/health/ready`, вход под тестовыми пользователями, права ролей, рецепты и печать A4, производственные листы, склад, ОТК, отгрузки, табель. Убедитесь, что данные тестовой базы сохранились после повторного деплоя. На CT48 проверьте сканирование QR + Enter.
Запустите тесты и `deployment_guard_v67.py` на тестовом стенде с резервной копией. Для работы HTTP-тестов установите зависимости.

## 6. Обновление рабочего приложения
Только после успешной проверки: окно обслуживания → новая резервная копия с выгрузкой за пределы Timeweb → остановка изменяющих операций → деплой той же проверенной версии → проверки работоспособности и контроль данных. При ошибках остановите запись и используйте заранее согласованный план отката (код + соответствующая резервная копия). Не восстанавливайте старую БД поверх новой без оценки данных, записанных после обновления.

## Ограничения
Этот пакет **не проверяет состояние вашей учётной записи Timeweb**, не гарантирует поддержку постоянного тома конкретным тарифом и не является подтверждением успешного деплоя. В среде подготовки не выполнены HTTP-интеграционные тесты Flask и реальный деплой.
